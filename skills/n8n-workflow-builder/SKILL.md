# n8n Workflow Builder

Use the connected n8n plugin to turn a user's workflow request into a working n8n draft. Start by presenting a compact plan, then build and verify it in the instance where the tools are connected. Do not stop after describing a hypothetical workflow when the user asked you to build one.

## Workflow

1. **Choose the right artifact.** If the user explicitly asks for an n8n workflow, build a workflow (including an AI Agent node if requested). If they ask for a first-class n8n Agent or assistant, use the Agent tools instead. Inspect existing workflows first when the user asks to modify one; otherwise create a new workflow.
2. **Translate the request into a plan before changing n8n.** State the trigger, key stages and branches, data passed between them, destination/action, credentials needed, assumptions, and how you will validate it. Keep this concise and readable. If a missing fact would change the design materially (such as the source account, event trigger, or destructive behavior), ask one focused question; proceed with independent discovery while waiting. Otherwise make a reasonable, visible assumption.
3. **Use n8n's planning guidance.** Call `get_workflow_best_practices` for each relevant technique before searching for nodes; call it with `technique: "list"` if unsure. Use its suggestions and known pitfalls to refine the plan.
4. **Ground every node in the connected instance.** Search for nodes, then call `get_node_types` with the returned node IDs and resource/operation/mode discriminators before configuring them. Do not guess node IDs, versions, parameter names, operation values, or credential types. Resolve resource-locator and dropdown values with `explore_node_resources` when possible, using the exact method and version from the node definition. If a suitable credential is not available for a lookup, use the documented ID-entry mode or leave the field for user setup; never fabricate an ID.
5. **Build the workflow.** For code-based creation or edits, read `get_workflow_sdk_reference` before writing SDK code. Run `validate_node_config` on node configurations and `validate_workflow` on the complete SDK code before create/update. For an existing workflow, inspect its current details and make the smallest focused update that fulfills the request. Resolve a named project with `search_projects`; never guess a project ID. Create or update a draft and inspect the result for validation warnings, skipped node groups/operations, and auto-assigned credentials. Repair incomplete work before calling it done.
6. **Handle credentials carefully.** Use `list_credentials` only to inspect metadata and find an existing, clearly matching credential; it does not reveal secret values. Reuse one only when its service/type and purpose clearly match the user's request. Never ask the user to paste a secret into chat, put secrets in workflow code, expressions, notes, examples, or HTTP headers, or claim a credential is configured just because a node exists. The connected tools do not create credentials: leave an unconfigured credential reference unset and explain how the user can add/select it in n8n. Review any automatic credential assignment returned by create/update and report it accurately.
7. **Validate and test safely.** Validate the stored workflow after creation/update. Prefer `prepare_workflow_pin_data` followed by `test_workflow` with realistic synthetic items to exercise logic while pinning triggers, credential-backed nodes, and HTTP requests. The test tool still runs unpinned nodes (including Code and file/command nodes), so inspect for external writes, messages, purchases, deletions, or other consequential effects first. Do not perform live actions just to test; use mocked/pinned data or static validation where a safe run is not possible. Report what passed and any coverage limits.
8. **Leave production activation deliberate.** A new workflow should remain a draft after building and testing. Publishing makes triggers, schedules, webhooks, and connected-app events live. Publish only when the user explicitly asks to activate/deploy it; otherwise explain the exact n8n steps to review and publish it. If publishing is requested, inspect the final workflow and test outcome first, then publish and verify the returned status.
9. **Close with a useful handoff.** Give the workflow name and clickable n8n URL when returned, summarize its trigger and behavior, list credentials or manual fields the user must supply, report validation/test results, and provide concise setup and deployment steps. Distinguish completed work from anything left for the user.
